The steps

1The two ways to commentA line or a block›

Two dashes hide everything after them on that line. The next line runs.

-- This whole line is ignored.
SELECT name, score  -- only this tail is ignored
FROM players;
namescore
Ana9
Bo3
Cy8

Slash-star opens a block and star-slash closes it. Line breaks do not end it.

/* Pulled for the third quarter review.
   Dana approved the numbers. */
SELECT name, score
FROM players;

A block has an end mark, so it can sit in the middle of a line. This returns 3.

SELECT 1 + /* this is skipped */ 2;

Which comment can sit in the middle of a line with code after it?

2Comment out a line safelyTrailing commas and stray AND›

You hide a line to test it. The line above can be left with punctuation that points at nothing. Both queries below fail on purpose.

Trailing comma

SELECT id,
-- name
FROM players;

Stray AND

SELECT id FROM players
WHERE score > 5 AND
-- status = 'active'
;
QuerySQLite says
Trailing commanear "FROM": syntax error
Stray ANDnear ";": syntax error

PostgreSQL and MySQL reject both too. DuckDB accepts the trailing comma.

Fix: start each line with its comma or AND. The punctuation is then hidden with the line.

This one runs

SELECT id
--   , name
     , status
FROM players
WHERE score > 5
--  AND status = 'active'
;
idstatus
1active
3inactive

The first column and the first condition are still exposed. For conditions, many people start with WHERE 1 = 1, which is always true, so every real condition begins with AND.

SELECT id
FROM players
WHERE 1 = 1
--  AND score > 5
  AND status = 'active';
id
1
2
Quick check

You often switch the last column on and off. Where does its comma go?

3Watch for silent changesA query that runs but does more›

An error is the easy case. A comment can also leave a query that runs and does something else. Here the WHERE line is hidden, so every row changes.

SQLite, PostgreSQL or MySQL (InnoDB tables). ROLLBACK undoes it.

BEGIN;
UPDATE players
SET status = 'inactive'
-- WHERE id = 2
;
SELECT id, status FROM players ORDER BY id;
ROLLBACK;
idstatus
1inactive
2inactive
3inactive
Before running UPDATE or DELETE, check that no comment mark hides the WHERE line. A SELECT with the same WHERE shows which rows it will touch.

Dashes inside quotes are text

Comment marks inside a quoted string do not start a comment. This returns a -- b.

SELECT 'a -- b';

The nesting trap

Wrapping lines in /* */ breaks when a block comment is already inside. In SQLite, MySQL, Oracle and BigQuery, the first */ ends everything.

Fails in SQLite and MySQL on purpose

/* switched off for now
SELECT customer_id,
       SUM(amount) AS total  /* shipped only */
FROM orders
WHERE status = 'shipped'
GROUP BY customer_id
*/

Everything from FROM orders down is live again. PostgreSQL, SQL Server and DuckDB nest block comments, so the same text is treated differently there. Line comments avoid the problem.

Safe version, followed by a live query

-- switched off for now
-- SELECT customer_id,
--        SUM(amount) AS total  /* shipped only */
-- FROM orders
-- WHERE status = 'shipped'
-- GROUP BY customer_id
SELECT COUNT(*) AS order_count FROM orders;
order_count
3

Test a query one join at a time

Hide a join, count the rows, then restore it and count again.

SELECT COUNT(*) AS row_count
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
-- JOIN payments p ON p.order_id = o.order_id
;
The payments line isrow_count

The count rose because order 1 has two payments. Check that before you add up amounts: why a join duplicates rows.

Keep the semicolon on its own line, so hiding the last join leaves it in place. Delete old experiments before you save the file.

All of these accept /* */. For SQL that may move between databases: put a space after --, close every block, and do not nest blocks.

The single-character comment

In MySQL, # hides the rest of a line. It also works in MariaDB and BigQuery. PostgreSQL reads # as an operator, and SQLite reports an error.

MySQL, MariaDB and BigQuery

SELECT 1 + 1;  # this note runs to the end of the line

MySQL needs a space after the dashes

MySQL treats -- as a comment only when a space or control character follows. Without it, the dashes can be read as minus signs.

SELECT 5--3;
Database testedResult
MySQL 8.08 (5 minus negative 3)
PostgreSQL 16, SQLite5 (the rest is a comment)

Nested blocks

SELECT 1 /* outer /* inner */ still hidden? */;
Database testedResult
PostgreSQL, DuckDBReturns 1
SQLite, MySQLSyntax error

A block left open

SQLite accepts a block with no */ and ignores the rest of the input. A script can then stop partway with no error. PostgreSQL, MySQL and DuckDB reported an error.

Comments that run

MySQL runs the text inside /*! */. This returns 2 in MySQL and 1 in PostgreSQL. Marks such as /*+ */ are used for optimizer hints in some databases, so do not start a note with ! or +.

SELECT 1 /*! + 1 */;

6Write comments worth keepingSay why, not what›

A comment such as -- keep active players above WHERE status = 'active' repeats the code. Record what a reader cannot work out: why a row is excluded, which unit a column uses, who agreed a rule and when.

-- Cy asked to be hidden from rankings
-- (example note: requester, date, reason).
SELECT name, score
FROM players
WHERE status = 'active'
ORDER BY score DESC;
namescore
Ana9
Bo3

For a full format, see commenting SQL so it teaches.

COMMENT ON is a different feature

COMMENT ON TABLE stores a description in the database. It does not stop code from running. Support differs by database: COMMENT ON TABLE.
