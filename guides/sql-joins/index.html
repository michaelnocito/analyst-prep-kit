SQL JOINs: How to Join Two Tables Without Losing or Doubling Rows

By Michael Nocito, implementation analyst · Updated November 27, 2026

A join can drop rows or repeat them without an error. Learn what each join keeps, then count to check it.

The habit: count rows and distinct keys before and after every join.
One inner join, drawn

Multiplied: Cave Crawl matches three reviews, so it takes three rows.

Dropped: Quiet Days and the review for game 99 have no match (✕).

The result has 4 rows. The tables had 3 and 5.

Practice data · made-up games and reviews

The steps

1What a join doesOne output row per matching pair›

Picture the database taking each row on the left and finding every row on the right that meets the ON condition. Each matching pair becomes one output row. (The engine may do the work in another order. The result is the same.)

SELECT g.name, r.hours
FROM games AS g
JOIN reviews AS r ON g.AppID = r.app_id
ORDER BY r.review_id;
namehours
Box Puzzle900
Cave Crawl174
Cave Crawl96
Cave Crawl310
  • No match: Quiet Days produces no row in this inner join.
  • Three matches: Cave Crawl produces three rows, and its game columns repeat on each.

games AS g gives a table a short name, so g.name means the name column of games. SQL aliases covers the habit.

Grain: what one row means

games has one row per game. reviews has one row per review. This join has one row per matched review, so a game value such as price can appear many times.

Say the grain of the result before you add anything up.
Quick check

A left row finds three matches. How many output rows does it make?

2Join typesWhat happens to rows with no partner›

The pair rule applies to joins with a condition. The types differ in which unmatched rows they keep.

JoinKeepsUse it when
INNERMatched pairs onlyA row with no partner is not part of the question
LEFTMatches, plus unmatched left rowsYou must keep your starting list
RIGHTMatches, plus unmatched right rowsOften rewritten as a left join with tables swapped
FULL OUTERMatches, plus unmatched rows from bothComparing two lists that should agree
CROSSEvery left row with every right rowBuilding a full grid on purpose

Where a side has no partner, its columns come back NULL (empty).

SELECT 'inner' AS join_type, COUNT(*) AS row_count
FROM games g JOIN reviews r ON g.AppID = r.app_id
UNION ALL
SELECT 'left', COUNT(*)
FROM games g LEFT JOIN reviews r ON g.AppID = r.app_id
UNION ALL
SELECT 'right', COUNT(*)
FROM games g RIGHT JOIN reviews r ON g.AppID = r.app_id
UNION ALL
SELECT 'full', COUNT(*)
FROM games g FULL OUTER JOIN reviews r ON g.AppID = r.app_id
UNION ALL
SELECT 'cross', COUNT(*)
FROM games CROSS JOIN reviews;

inner44 matched pairs
left54 pairs + Quiet Days
right54 pairs + review for game 99
full64 pairs + both leftovers

SQLite needs version 3.39 or later for RIGHT and FULL OUTER JOIN. MySQL 8.0 has no FULL OUTER JOIN.

Self join: one table, two names

A self join is not a keyword. It joins a table to itself, here to find each person’s manager.

WITH staff(staff_id, name, manager_id) AS (
  VALUES (1,'Rosa',NULL), (2,'Dev',1), (3,'Mei',1)
)
SELECT e.name AS employee, m.name AS manager
FROM staff AS e
LEFT JOIN staff AS m ON e.manager_id = m.staff_id
ORDER BY e.staff_id;
employeemanager
RosaNULL
DevRosa
MeiRosa

Syntax you will see

  • Plain JOIN means INNER JOIN in the common databases.
  • LEFT OUTER JOIN is the same as LEFT JOIN.
  • ON states the match. USING (app_id) is shorthand when both tables use that column name.
  • Leave out ON and SQLite and MySQL pair every row with every row. PostgreSQL raises an error.
  • A match on something other than equals, such as a date inside a range, is a non-equi join. It can multiply rows too.

Which join keeps every game, reviewed or not, with games on the left?

3Rows that disappearCount what went in and what came out›

An inner join leaves out rows with no match. It raises no error. First count the games that have at least one review.

SELECT COUNT(DISTINCT g.AppID) AS games_with_reviews
FROM games AS g
JOIN reviews AS r ON g.AppID = r.app_id;
games_with_reviews
2

The check

Compare rows in with distinct keys out. This works when AppID is filled in and unique in games.

SELECT COUNT(*) AS rows_in FROM games;

SELECT COUNT(DISTINCT g.AppID) AS keys_out
FROM games AS g
JOIN reviews AS r ON g.AppID = r.app_id;
rows_inkeys_outMatch rate
322 of 3 games (67%)

If keys_out is smaller, decide: is the drop correct, or do you need a LEFT JOIN? Write the match rate beside the result.

The anti-join: list what found nothing

SELECT g.name, g.price
FROM games AS g
LEFT JOIN reviews AS r ON g.AppID = r.app_id
WHERE r.app_id IS NULL;
nameprice
Quiet Days5.0

A matched row has a value in r.app_id, because the equals match needs one. So IS NULL keeps only the unmatched games. Then ask why they are missing: bad ids, late data and real gaps need different fixes. Documenting data limitations shows how to write it up.

Quick check

3 games go in and 2 distinct ids come out. What happened?

4Rows that multiplyWhy a total comes out too high›

Cave Crawl costs 7.00 and has three reviews. Add up its price after the join:

SELECT g.name, SUM(g.price) AS total_price
FROM games AS g
JOIN reviews AS r ON g.AppID = r.app_id
GROUP BY g.AppID, g.name
ORDER BY g.AppID;
nametotal_price
Box Puzzle3.0
Cave Crawl21.0

No error. The price was added once per review. This is fan-out.

The check

SELECT COUNT(*) AS joined_rows,
       COUNT(DISTINCT g.AppID) AS distinct_games
FROM games AS g
JOIN reviews AS r ON g.AppID = r.app_id;
joined_rowsdistinct_games
42

More rows than keys means some game repeats. That is expected in a one-to-many join. It matters when you total or average as if it had not happened.

Averages can be wrong too

SELECT AVG(g.price) AS per_joined_row,
  (SELECT AVG(price) FROM games
   WHERE AppID IN (SELECT app_id FROM reviews)) AS per_game
FROM games AS g
JOIN reviews AS r ON g.AppID = r.app_id;
per_joined_rowper_game
6.05.0

Cave Crawl appears three times and Box Puzzle once, so the first average leans toward Cave Crawl. Inside one game’s group the price is the same on every row, so that group’s average stays right.

Do not SUM, COUNT or AVG a one-side column across repeated rows unless you mean to weight it. To show the price, add it to GROUP BY.

Group, then filter with HAVING

SELECT g.name,
       g.price,
       COUNT(r.review_id) AS num_reviews,
       ROUND(AVG(r.hours), 1) AS avg_hours
FROM games AS g
JOIN reviews AS r ON g.AppID = r.app_id
GROUP BY g.AppID, g.name, g.price
HAVING COUNT(r.review_id) >= 2
ORDER BY avg_hours DESC;
namepricenum_reviewsavg_hours
Cave Crawl7.03193.3

WHERE filters rows before grouping and cannot use this count. HAVING filters the groups. A floor of 2 suits five practice rows; pick yours from the data (data-driven thresholds).

Quick check

A 7.00 game matches three reviews. What is SUM(g.price)?

6Joins that surprise youTypes, text, NULLs, many-to-many, speed›

The keys have different names

games.AppID and reviews.app_id can still match. The values and their meaning matter, not the names.

The keys look alike but are not equal

Leading zeros and stray spaces can make a text join return nothing.

WITH price_list(code) AS (VALUES ('0010'), ('0020')),
     sales(code) AS (VALUES ('10'), ('20 '))
SELECT
  (SELECT COUNT(*) FROM sales s
   JOIN price_list p ON s.code = p.code) AS raw_matches,
  (SELECT COUNT(*) FROM sales s
   JOIN price_list p
     ON CAST(TRIM(s.code) AS INTEGER)
      = CAST(p.code AS INTEGER)) AS cleaned_matches;
raw_matchescleaned_matches
02

Convert to numbers only when the codes are all digits and the zeros carry no meaning.

A number column joined to a text column behaves differently by database: PostgreSQL raises an error for integer = text, while SQLite and MySQL may convert and match. Check the stored types on both sides.

True and false stored as text

SELECT
  SUM(is_recommended = 1) AS equals_one,
  SUM(is_recommended = 'true') AS equals_true
FROM reviews;
equals_oneequals_true
03

In SQLite the first test finds nothing and still looks like an answer. Look at the distinct values before filtering.

NULL in the join key

WITH a(k) AS (VALUES (1), (NULL)),
     b(k) AS (VALUES (1), (NULL))
SELECT COUNT(*) AS matched
FROM a JOIN b ON a.k = b.k;
matched
1

With =, NULL does not match anything, even another NULL. Count missing keys with WHERE key_column IS NULL. If two blanks should match, databases have their own operators for that; check that you really mean it.

Many-to-many

Three rows on one side and two on the other, with the same key, make six.

WITH tags(app_id, tag) AS (VALUES (20,'cave'), (20,'rpg'))
SELECT COUNT(*) AS joined_rows, SUM(r.hours) AS hours_total
FROM reviews AS r
JOIN tags AS t ON r.app_id = t.app_id;
joined_rowshours_totalTrue hours
61160580

If you need one row per key, aggregate one side first, then join.

WITH tags(app_id, tag) AS (VALUES (20,'cave'), (20,'rpg')),
tag_counts AS (
  SELECT app_id, COUNT(*) AS tag_count
  FROM tags GROUP BY app_id
)
SELECT t.tag_count, SUM(r.hours) AS hours_total
FROM reviews AS r
JOIN tag_counts AS t ON r.app_id = t.app_id
GROUP BY r.app_id, t.tag_count;
tag_counthours_total
2580

A slow join

An index on the join key can help a large join. Check the query plan before and after.

CREATE INDEX IF NOT EXISTS idx_reviews_app_id
ON reviews (app_id);

EXPLAIN QUERY PLAN
SELECT g.name, r.hours
FROM games AS g
JOIN reviews AS r ON g.AppID = r.app_id;

Look for idx_reviews_app_id in the plan. EXPLAIN QUERY PLAN is SQLite’s form. An index takes space, and the database may choose not to use it. See when to index and handling large datasets.

The tables describe different moments

Two lists pulled on different dates can miss each other for that reason alone. Record where and when each came from.

7Your JOIN doubled a totalFind the repeat, then pick a fix›

Revenue is higher than finance says. Nothing errored. Often a join matched one row to several, and a one-side value was added more than once.

Set up two new tables

CREATE TABLE orders(order_id INT, customer_id INT, amount INT, status TEXT);
INSERT INTO orders VALUES
(101,1,120,'shipped'),(102,1,80,'shipped'),
(103,2,200,'cancelled'),(104,2,50,'shipped'),
(105,3,300,'shipped'),(106,4,90,'pending'),
(107,4,60,'shipped'),(108,5,150,'cancelled');

CREATE TABLE payments(payment_id INT, order_id INT, amount INT);
INSERT INTO payments VALUES
(1,101,60),(2,101,60),(3,102,80),
(4,104,50),(5,105,300),(6,107,60);

Eight orders totaling 1,050. Six payments. Order 101 was paid in two parts of 60.

The query that goes wrong

SELECT COUNT(*) AS row_count, SUM(o.amount) AS order_total
FROM orders o
JOIN payments p ON p.order_id = o.order_id;
row_countorder_totalTrue total of the 5 paid orders
6730610

Order 101 appears twice, so its 120 counts twice: 120 + 80 + 50 + 300 + 60 = 610, plus 120 again.

Find the repeating key

SELECT COUNT(*) AS order_rows FROM orders;

SELECT COUNT(*) AS joined_rows,
       COUNT(DISTINCT o.order_id) AS joined_orders
FROM orders o
JOIN payments p ON p.order_id = o.order_id;

SELECT order_id, COUNT(*) AS payment_rows
FROM payments
GROUP BY order_id
HAVING COUNT(*) > 1;
QueryResult
Orders8
Joined rows, orders6, 5
Repeating key101, with 2 rows

The inner join dropped 3 unpaid orders and repeated 1. A single row count can hide both, so count distinct keys too.

Fan-out compounds. If one order has 2 payments and 3 shipments, joining all three gives 2 × 3 = 6 rows for it. Check after each join.

Fix 1: total the many side first

SELECT o.order_id, o.amount, COALESCE(p.paid, 0) AS paid
FROM orders o
LEFT JOIN (
    SELECT order_id, SUM(amount) AS paid
    FROM payments
    GROUP BY order_id
) p ON p.order_id = o.order_id
ORDER BY o.order_id;
ResultOrder 101
8 rows, one per orderamount 120, paid 120

The subquery has one row per order id, so it cannot multiply orders (given unique order ids). COALESCE shows 0 for no payment.

Fix 2: EXISTS, when you only need a yes or no

SELECT COUNT(*) AS paid_orders, SUM(amount) AS order_total
FROM orders o
WHERE EXISTS (SELECT 1 FROM payments p
              WHERE p.order_id = o.order_id);
paid_ordersorder_total
5610

EXISTS keeps or drops each order row. Extra payments cannot repeat it.

Fix 3: total the many-side column

SELECT COUNT(DISTINCT o.order_id) AS orders,
       SUM(p.amount) AS paid
FROM orders o
JOIN payments p ON p.order_id = o.order_id;
orderspaid
5610

Each payment appears once here, so its amount can be summed. A second one-to-many join would break that. SUM(o.amount) is still 730.

Why DISTINCT is not the fix

SELECT SUM(DISTINCT o.amount) AS order_total,
       SUM(DISTINCT p.amount) AS paid_total
FROM orders o
JOIN payments p ON p.order_id = o.order_id;
ColumnResultCorrect
order_total610610, by luck
paid_total490610

DISTINCT inside SUM removes equal values, not repeated rows. Three real payments of 60 count once. The order total works only because no two of these orders share an amount.

Two different payments are both 60. What does SUM(DISTINCT amount) do?

On your next join

  1. Say what one row of each table means.
  2. Check that the key you expect to be unique is unique.
  3. Count rows and distinct keys before and after each join.
  4. Run the anti-join once.
  5. Write the match rate beside the result.
  6. Compare the total with a trusted figure when you have one.

Keep one habit

Before you write FROM, say what one row of the result will mean.
